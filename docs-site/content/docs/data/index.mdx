This section covers everything that holds state in LogiStack: the databases you run, the backups that protect them, the S3 buckets those backups go to, object storage for your apps, files in volumes, and cron jobs. Read it when you need to look inside a database, set up backups before going to production, or recover from a mistake.

## What each part does

- The **Database** tab of a database service is a built-in explorer. You browse tables, edit rows, run SQL, manage roles and download or restore a dump without a separate client.
- A **backup policy** dumps a database, or archives a volume, to an S3 bucket on a cron. It keeps as many copies as you choose and can encrypt them with [age](https://age-encryption.org).
- The **restore wizard** brings a backup back, into the service itself or into a copy beside it.
- **S3 destinations** are the buckets backups write to: AWS S3, Cloudflare R2, Backblaze B2, Hetzner, MinIO, Wasabi or any S3-compatible store.
- **Object storage** services run an S3-compatible server (MinIO, RustFS, Garage or SeaweedFS) in your project, with a file browser, scoped keys and share links.
- The **Files** tab shows a service's config files and volumes, and lets you browse the running container's filesystem.
- **Schedules** run a shell script on a cron, in a fresh container, inside a service or on a node.

## A typical setup

1. Deploy a database, for example PostgreSQL. See [Databases](../deploy/databases.mdx).
2. Add an [S3 destination](./s3-destinations.mdx) that lives off the server, such as an R2 or B2 bucket.
3. Create a [backup policy](./backups.mdx) on the database with encryption on, and save the key somewhere outside the server.
4. Turn on scheduled verifies, so LogiStack restores the newest backup into a throwaway container every week and tells you if it fails.
5. Practice a [restore into a copy](./restore.mdx) once, before you need it.

---
title: Secrets and environment variables
description: Store secrets encrypted and versioned at the organization, folder, project, environment or service level, reference them from services, and share plain variables across scopes.
---

Environment variables configure a service without changing its image: database URLs, API keys, feature flags. LogiStack keeps two kinds apart:

- **Secrets** are encrypted, versioned and audited. You define a secret once, at the level that owns it, and every service below that level can reference it. A service gets a secret only when its **Environment** tab references it.
- **Variables** are plain configuration. They cascade to every service in their scope.

Both are applied on the next deployment. Secrets can also live in HashiCorp Vault, Infisical or 1Password and be read at deploy time: see [External secrets](./external-secrets.mdx).

## Where secrets live

A secret is defined at one of five levels. A service can reference any secret defined on its own chain:

1. **Organization**: available to every service.
2. **Folder** and subfolder: available to every project inside.
3. **Project**: available to every service in the project.
4. **Environment**: available to every service in one environment, like the Production database password.
5. **Service**: available to that service only.

When two levels define the same key, the picker marks the less specific one as shadowed. For example, with `STRIPE_KEY` on the organization and on the Clients folder, services in Clients see the folder's as the first choice.

<Steps>
<Step>

### Open Secrets & variables

- **Organization or folder**: select **Settings** › **Secrets & variables**. Pick the level in **Defined for**: the whole organization or one folder.
- **Project or environment**: open the project's actions menu (**⋯**) and select **Secrets & variables**, then pick the project or one environment.

![The Secrets & variables page of the Storefront project, Production selected, with the secret DATABASE_PASSWORD at version 2 used by 7 services](/screens/project-variables.webp)

</Step>
<Step>

### Add it

On the **Secrets** tab, select **Add secret**. Enter the key, the value and, optionally, a description such as "Transactional email, rotated by ops". Select **Add secret**.

</Step>
<Step>

### Reference it from a service

Open the service, select **Environment**, then **Add**. Type the name the container should see, select **Secret** and pick the secret from the list. The list groups secrets by where they are defined. The name in the container can differ from the secret's key: `DB_PASSWORD` can point at `PROD_PG_PASSWORD`.

</Step>
<Step>

### Save

Select **Save and redeploy** to apply at once, or **Save** to apply on the next deployment.

</Step>
</Steps>

## Type a secret directly on a service

On a service's **Environment** tab you can also select **Text**, type the value and turn on **Secret**. The toggle turns on by itself when the name looks sensitive (`PASSWORD`, `TOKEN`, `KEY`, `SECRET`, `CREDENTIAL`, `PRIVATE`). When you save, LogiStack stores the value as a secret of that service and references it, so every secret is managed in one place. **Review before saving** lists which keys become secrets and which stay plain variables.

Removing the variable also removes that service secret, unless something else references it.

To add many at once, select **Paste .env**. The preview shows which keys will become secrets.

```bash title=".env"
STRIPE_SECRET_KEY=sk_live_51H...
PUBLIC_URL="https://shop.example.com"
LOG_LEVEL=warn
```

## See, change and roll back a secret

On the **Secrets** tab:

- The eye button shows the value. It needs the read secrets permission on the secret's level, and every reveal is recorded in the [audit log](../team/audit-log.mdx) as `secret.reveal`. The value hides again after 20 seconds.
- **Edit value** saves a new version. Services that reference the secret show the change in [Review changes](./deployments.mdx#review-changes-before-deploying) until they redeploy.
- **History** lists every version with its author. **Roll back** copies an earlier value as a new version.
- **Usages** lists the services that reference the secret. **Delete** is unavailable while it is in use.

Values never appear in variable lists, the API's variable endpoints, manifests, the audit log or deployment logs. Build and deployment logs replace any secret value, and its base64 form, with `***`.

## How secrets are encrypted

Each organization has its own data key. Every secret version is encrypted with AES-256-GCM under that key and bound to its organization, secret and version number, so a value copied into another row does not decrypt. Data keys are themselves encrypted with a key derived from the instance master key, which never leaves the LogiStack containers.

An organization admin can select **Rotate encryption key** on **Settings** › **Secrets & variables**. LogiStack creates a new data key and re-encrypts every secret version. Values, versions and references don't change.

## Plain variables

The **Variables** tab holds plain variables at four scopes. When the same key is set at more than one, the most specific wins: **Organization**, **Project**, **Environment**, then **Service**.

For example, with `LOG_LEVEL=info` at the organization and `LOG_LEVEL=warn` on Production, every Production service gets `warn` and every other service gets `info`.

On a service, the **Inherited** panel lists the plain variables it gets from the organization, project and environment. A crossed-out row is overridden by a more specific one. **Override for this service** copies the key and value into **Service variables** for you to edit.

Mark a variable **Build** to also pass it to the build. Plain build variables become Dockerfile build arguments; secrets become BuildKit secrets. See [Build types](./build-types.mdx#build-time-variables-and-secrets).

## With the API

The same operations are available over the API and the MCP server (`secret_create`, `secret_reveal`, and so on).

```bash title="Create a Production database password"
curl -fsS -X POST "https://stack.example.com/api/secrets" \
  -H "x-api-key: $LOGISTACK_API_KEY" \
  -H "content-type: application/json" \
  -d '{
    "scope": "environment",
    "scopeId": "env_storefront_production",
    "key": "PG_PASSWORD",
    "value": "s3cret-2026"
  }'
```

`scope` is `organization`, `folder`, `project`, `environment` or `service`. To reference it, send `{"key": "DB_PASSWORD", "secretId": "sec_...", "isSecret": true, "isBuildTime": false}` in `PUT /api/services/{id}/env-vars`. `POST /api/secrets/{id}/reveal` returns the value.

Secret variables created the older way, through `POST /api/env-vars` or a [project manifest](../automation/project-manifests.mdx) with `secret: true`, are converted into secrets on the next deployment. Every service that received one keeps receiving it through a reference.

## Variables set on every deployment

LogiStack sets these on every container. They are read-only, and names starting with `LOGISTACK_` are reserved for them.

| Variable | Value |
|---|---|
| `LOGISTACK_DEPLOYMENT_ID` | The deployment that started this container |
| `LOGISTACK_COMMIT_SHA` | Full hash of the deployed commit. Git sources only |
| `LOGISTACK_COMMIT_MESSAGE` | First line of the commit message, up to 200 characters. Git sources only |
| `LOGISTACK_BRANCH` | Branch the commit was built from. Git sources only |
| `LOGISTACK_ENVIRONMENT` | Name of the environment |
| `LOGISTACK_PROJECT` | Name of the project |
| `LOGISTACK_SERVICE` | Name of the service |
| `LOGISTACK_URL` | Primary domain with its scheme, such as `https://app.example.com`. Unset without a domain |
| `LOGISTACK_FQDN` | Every hostname the service answers on, comma-separated. Unset without a domain |
| `LOGISTACK_PREVIEW_URL` | Pull request previews only: the preview's main URL. See [Preview environments](./preview-environments.mdx#reach-one-service-from-another) |
| `LOGISTACK_PREVIEW_URL_<SERVICE>` | Pull request previews only: the URL of each exposed service of the preview, such as `LOGISTACK_PREVIEW_URL_API` |

A Dockerfile build gets the ones it declares with `ARG`:

```dockerfile
ARG LOGISTACK_COMMIT_SHA
ENV SENTRY_RELEASE=$LOGISTACK_COMMIT_SHA
```

## Check that it worked

Open the **Terminal** tab and print the variable:

```bash
printenv LOG_LEVEL
```

If it shows the old value, the service hasn't been redeployed since the change. Select **Deploy**.

## Common problems

- **"Secret not available"**: the service references a secret that is no longer on its chain, for example because its project moved to another folder. Select **Fix** and pick another secret.
- **A secret can't be deleted**: it is in use. Open **Usages** and remove the references first.
- **A secret is missing from the picker**: it is defined on another branch, or you lack the read permission on its level.
- **"Defined twice"**: the same name appears on two rows. Keep one.
- **A reserved name is refused**: names starting with `LOGISTACK_` belong to the deployment context variables. Rename yours.
- **A build can't see a variable**: check its **Build** box and declare it with `ARG` in the Dockerfile.
